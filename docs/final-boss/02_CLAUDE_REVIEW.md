# Claude批評 — 祭典終端巨人「ティウ」を「大きいだけの再利用ボス」で終わらせないために

対象: `01_CODEX_CONCEPT.md`（Codex初案）。参照した実データ: `bosstiu/*.fbx`（41ボーン、T-Pose本体 46,895頂点/93,790ポリゴン、実測クリップ尺は01案の表の通り）、`output/texture_report.json`（`boss_textured.glb` は `armature_count: 0` = 無骨格）、および `src/data/bosses.js` `src/engine/bosses.js` `src/engine/targets.js` `src/engine/webswing.js` `src/engine/step.js` `src/scene/ThirdPersonCamera.jsx` `src/gfx/BossModel.jsx`。

総評: Codex案は要件を満たす骨格として健全で、部位HP・破壊因果・実装順序はそのまま使える。だが「巨大な的を安全な手順で殴るコンテンツ」の域を出ておらず、このままでは既存4ボスの延長線に見える。以下、要求された17項目に沿って指摘する。

---

## 1. Codex案の強い点

- 出現条件・HP計算・攻撃入口をすべて `damageTarget` / `sim.bossProgress` に載せており、既存4ボスの状態機械を壊さない設計になっている（`spawnBoss` 相当の再利用、`arena.js` の `ARENA.maxRadius: 84` に対して提案アリーナ半径52mは収まる）。
- 「片脚を折る→前腕を坂にする」という乗り方は透明エレベーターを避けており、要求6.2の禁止事項を満たしている。
- 部位破壊が見た目・攻略ルート・攻撃停止の3つに同時に効く設計（11章の表）は、部位破壊システムとして十分な深さがある。
- `bosstiu` のクリップ尺・ボーン数・頂点数を実測し、存在しない前提を置いていない。`boss_textured.glb` が `armature_count: 0`（無骨格）である点も正しく捉え、T-Poseスキン側へテクスチャを移す方針にしている。
- 性能予算（12 draw calls、Collider数上限、破片数、LOD）が数値化されており、実装フェーズでそのまま検証項目にできる。

## 2. 平凡または既視感がある点

- 「巨人の脚を折って登り、光る弱点を壊し、コアを暴いて倒す」は構造として『ワンダと巨像』『ゴッド・オブ・ウォー』『モンスターハンター』の乗り撃破の定型そのもの。骨格を否定はしないが、01案には**この巨人だけの固有ルール**がまだ無い。9個の足場・7系統の部位はいずれも「既存の攻撃を大きくしただけ」に見える危険がある。
- 「4体の力を吸収し、4色の導管として身体に宿す」は良い着想だが、実装内容（`four_echoes` = 既存ボス攻撃の縮約再生）は文字通りの技の使い回しであり、プレイヤーには「前に見た攻撃が小さく飛んでくる」以上の新規性が伝わらない。
- 死亡演出「発光ルートを逆走して手のひらへ」は『ワンダと巨像』の崩落からの生還、『ゼルダ ブレワイ』のガーディアン系撃破と印象が近い。差別化点（このゲーム独自の理由付け）が本文にまだ無い。
- P1→P2→P3→P4の直線的なフェーズ進行は既存4ボスの「フェーズ1→フェーズ2」の延長でしかなく、「巨大ボスだからできる構成」になっていない。

## 3. 巨大ボスなのに小さく感じる点（最重要・技術的根拠あり）

**カメラ距離の上限がコードで16mに固定されている。** `src/engine/step.js:134`

```js
c.dist = THREE.MathUtils.clamp(c.dist, preview ? 1.5 : 3.5, preview ? 80 : 16)
```

これは通常プレイ中ずっと効く制約で、Codex案17章の「登場時だけ最大30mへ滑らかに遷移」は**入場演出の一時的な例外**としてしか書かれていない。戦闘本編（P1〜P4）のカメラ距離は7〜28mと書かれているが、実際のホイール/2本指スクロール入力は16mで頭打ちになる。36mの巨人に対して常時16m以内から見上げる形になり、**プレイ中の大半で全身が画角に入らない**。これは「巨大感を操作・カメラ・音で感じるか」という完成条件（プロトコル6章）に直結する欠陥であり、宿題として明示する（17項目目参照）。

- `ThirdPersonCamera.jsx` の `cameraDistance()` はベイク済みの静的地形/建物の遮蔽だけを見ており、動くボス本体は遮蔽物として扱われない。カメラがボスの体内へめり込む/貫通するリスクをCodexは17章で認識しているが、実装方法（簡略カプセルとの線分判定）はまだコード上どこにも存在しない新規モジュールで、01案の技術的リスク一覧（24章）に載っていない。
- 射程の短い近接攻撃（`hitRadius` ベースの既存判定）をそのまま使うと、36m級の的では「攻撃が当たっているように見えない」既視感が出る。部位ごとに当たり判定を独立させる設計（9章）は正しいが、視覚的なヒットフィードバック（部位が実際に近距離で見えるカメラの寄り）との連携が本文にない。

## 4. 身体上戦闘が形だけになっている点

01案7章の足場ルールは「傾斜角で歩行/滑落が決まる」だけで、**地上の通常戦闘と同じ入力・同じ武器・同じ`damageTarget`呼び出しを、動く床の上でやるだけ**になっている。身体の上にいることの意味が「攻撃対象が近くなる」以上に無い。

- グリップ帯（縁で1秒耐える）は落下猶予装置であって、戦術選択ではない。
- 9個の足場は役割が名前しか割り振られておらず（19章に例はあるが本文の攻撃表に反映されていない）、例えば「肩に乗っているときだけ使える行動」が存在しない。
- 既存の `webswing.js` は建物の破片・地形にしか糸を張れない（`registry.parts` 依存）。ボス本体は現状この対象に含まれておらず、01案でも「ウェブ習得済みなら肩・腰の発光アンカーへ短縮できる」とあるが、ボス本体をアンカー対象に追加する実装方針が書かれていない＝身体上移動の主力候補がまだ絵に描いた餅。

## 5. 4ボス撃破との関係が弱い点

- 4体撃破の**結果として得たアイテム**（`prototype_core` `stage_pass` `boundary_seal` `chef_medal`、`sim.player.items` に実在）が、ラスボス戦のどこにも使われていない。四祭導管の色対応だけでは「撃破した実感」がUIの色分け止まりになる。
- `sim.bossProgress.order`（撃破順）も一切参照されない。同じ4体を倒しても毎回まったく同じラスボス戦になり、「4ボス撃破後だから成立する」要件（プロトコル1章3項、9.1節）を演出面でしか満たしていない。
- 導管破壊で「対応する4ボス由来攻撃を1つずつ停止」は良い着想だが、停止するだけで、プレイヤーが**その4ボスへの理解**（弱点属性、突破法）を再利用できる場面が無い。既存ボスの `weakness` 属性（thunder/dark/water）をラスボス戦の攻略に絡めていない。

## 6. 登場演出の再設計

01案4章の「光柱→頭部が地平線から上がる」は定番の巨大ボス演出で、かつ上記3項の通りカメラが実際には全身を収める設計になっていない。以下へ差し替える。

**再設計: 「祭壇の再構築」**
4体目撃破の瞬間、倒した4ボスの残骸（`sim.ragdolls` に残る撃破後のラグドール、`defeatBoss` で `spawnRagdoll` 済み）が地面から浮き上がり、広場中央へ吸い寄せられて、プレイヤーの目の前で**巨人の脚部として再構築される**。頭部から始まる遠景の見上げではなく、**地面（プレイヤーの足元）から立ち上がる巨人**にすることで、カメラを持ち上げずに「見上げる動作」自体で高さを体感させる。

- 面白さの理由: 既存4体の死体が使い回されるのではなく「素材」になる。壊した建物・倒した敵の残骸をこのゲームは既に物理オブジェクトとして持っている（`ragdoll.js` `debris.js`）ので、演出のためだけの新規アセットを増やさずに実現できる。
- プレイヤーの操作: 操作は維持したまま、カメラだけ強制的に伏せた低い位置へ寄る（`sim.camera.pitch` を一時的に負値へ）。プレイヤーは歩いて後ずさることができる。
- 実装コスト: 中。既存ラグドール座標を補間で巨人のスポーン座標へ寄せるアニメーションのみで、新規モデルは不要（見た目はパーティクルと発光メッシュで隠す）。
- 技術リスク: ラグドール消滅タイミングと巨人スポーンの同期がズレると違和感が出る。`defeatBoss` 側でラグドール寿命を延長するフラグが必要。
- 簡略版: ラグドール再構築を省略し、単に地面の砂塵越しにシルエットが立ち上がる（カメラだけ低くする効果は残す）。

## 7. フェーズ構成の再設計

01案のP1〜P4は「地上→登攀→頭部→死亡」の一本道。**登攀を独立フェーズにせず、全フェーズを通して常時使う移動手段にする**ことで、身体の上にいる時間を長くし、行き来自体をゲームプレイにする。

**再設計フェーズ**

| フェーズ | 呼称 | 主目的 | ボスの状態 |
|---|---|---|---|
| P0 | 祭壇の再構築 | 演出、安全時間 | 不動 |
| P1 | 二本の脚 | 左右すねを地上から攻略、片脚破壊で膝つき | 徘徊・踏みつけ |
| P2 | 身体は戦場 | 4祭導管を任意順で破壊。登攀・落下・再登攀がフェーズの主動作 | 歩行、時々振り払い |
| P3 | 視界を奪う | 視界冠破壊で頭部ルート開放。導管を残したまま突入も可（難度上昇） | 追尾強化、振り払い頻度増 |
| P4 | 祭核 | 露出した核と近接、脈動を避けながら攻撃 | 直立、攻撃激化 |
| P5 | 最後の降下 | 死亡シーケンス中の脱出行動 | 崩落 |

P2とP3の境界を緩め、視界冠を先に壊してから導管を仕上げるプレイも許可する（01案は「頭部攻撃を止めると胸へのルートが開く」と書いており事実上順序固定に見えるため、ここを明確に自由化する）。

## 8. 身体そのものを活用する新攻撃

01案の攻撃表は「地上ボスの技を大きくしただけ」に見えるため、**身体の破壊状態そのものが攻撃のソースになる**ものを追加する。

- **`debris_shed`（瓦礫振り落とし）**: `shoulder_roll` の発展形。身震いで、すでに破壊済みの部位から生じた瓦礫（`targets.js` の `structureStrike` が生む破片オブジェクト）が足場上を転がり落ちる。プレイヤーは踏みつけではなく「転がってくる自分が壊した瓦礫」を避ける。
  - 面白さ: 自分の攻撃の結果（破壊した部位の残骸）が後から自分に返ってくる、部位破壊とリスクを直結させる。
  - 操作: 足場上での回避（既存のダッシュ/ジャンプ入力を流用）。
  - 実装コスト: 中。破片オブジェクトの発生源を `structureStrike` の破壊イベントへフックし、足場Colliderとの衝突判定だけ追加。
  - 技術リスク: 動く足場上での剛体挙動は不安定になりやすい。数を1〜2個に絞れば許容範囲。
  - 簡略版: 瓦礫を出さず、既存の `bossHazard` エフェクト（`oil` と同じ仕組み）で「危険地帯が足場上を移動する」だけにする。
- **`grip_shake`（振り落とし）**: 前腕・肩が登攀路化した状態で使用可能になる専用攻撃。今掴んでいる足場だけを狙って揺らし、他の足場は揺れない。
  - 面白さ: 「安全に見えた登攀路が実は攻撃対象になる」という部位破壊の皮肉な効果。全身が一様に揺れる`shoulder_roll`より読み合いが生まれる。
  - 操作: 揺れの警告（発光帯の点滅）に対してグリップ帯へ寄るか隣の足場へ飛び移る。
  - 実装コスト: 低。既存の足場Collider変換に一時的な追加回転を掛けるだけ。
  - 技術リスク: プレイヤーが空中に投げ出された場合の受け（10項）と連動させないと理不尽になる。
  - 簡略版: 揺れ演出だけにして落下判定を無くし、視覚的な緊張感のみ提供する（MVP向け）。
- **`conduit_backlash`（導管逆流）**: 破壊した祭導管の色が、対応する4ボスの弱点属性で一時的にボス自身を弱体化させる代わりに、破壊直後の数秒だけその属性の反撃技をボスが繰り出す（例: thunder導管破壊直後は帯電した腕払い）。
  - 面白さ: 部位破壊が「安全になる」だけでなく「一瞬だけ危険になる」ことで、壊した直後の油断を咎める。4ボスの個性を攻撃として最後にもう一度見せる。
  - 操作: 破壊直後の警告テレグラフに対する回避。
  - 実装コスト: 低〜中。既存の4ボス `abilities` 定義を参照して該当技を1つ選び、`fireBolt`/`circle` など既存関数へ渡すだけ。
  - 技術リスク: 低い。既存のダメージ経路をそのまま使える。
  - 簡略版: 専用モーションを作らず、既存の発光エフェクトと既存の `bolt` 攻撃だけで表現する。

## 9. 部位破壊の意外な因果関係

01案11章の因果（脚破壊→移動低下、腕破壊→登攀路化）は妥当だが、すべて「弱くなる」方向にしか効いていない。**部位破壊が新しい脅威や新しい攻略ルートを同時に開く**因果を足す。

- 視界冠破壊 → 単なる追尾低下ではなく、**ボスが盲目のまま建物へ突っ込む**（`damageStructure` を使った意図的な自傷可能な暴走）。プレイヤーはこれを誘導することで大ダメージを狙えるが、崩れる建物の破片に自分も巻き込まれるリスクを負う。
- 両すね破壊 → 「膝つき時間+3秒」だけでなく、**両膝つき状態は専用の低姿勢フェーズ**になり、通常は届かない胸元に地上から直接攻撃できる短い窓が生まれる（登攀を選ばない攻略ルートの提示）。
- 四祭導管を4本とも同時に破壊できた場合（通常は順不同で個別破壊）、ボーナスとして胸核の露出時間が延長される「連鎖破壊」判定を用意し、部位破壊の**順序・速度**にも意味を持たせる。

## 10. プレイヤーが落下するだけにならない工夫

01案18章の「光の糸で引き戻す」は安全だが、失敗が無風になりすぎる。**落下を意味のある選択に変える**。

- 落下開始時、`webswing.js` の `findAnchor` をボス本体の破壊済み部位（登攀路化した前腕など）へも対象を広げ、**自動引き戻しではなく、プレイヤー自身が糸を撃って復帰できる猶予**を与える。糸を撃てなかった場合のみ、01案の光の糸で救済する。
- 面白さ: 落下は「死」ではなく「もう一つの操作の見せ場」になる。既存のウェブスイング操作をそのままボス戦のクライマックスで使い切れる。
- 操作: 落下中にQ（既存の `tryWebAttach` 相当）でボス本体の登攀路化部位へ糸を張る。
- 実装コスト: 中。`findAnchor` の探索対象にボスの部位Colliダーを追加し、`registry.parts` 依存のロジックを分岐させる必要がある。
- 技術リスク: ボス本体は常に動くため、静的な `raycastStructure` と同じ処理では成立しない。動くターゲット用の簡易版（部位Colliダーへの直接距離判定）を別途用意する必要がある。
- 簡略版: 自動引き戻しのみ（01案のまま）。ただし引き戻し回数に上限を設け、連続失敗時は地上P1相当へ強制送還してテンポを守る。

## 11. 地形・建物・空・画面全体を使った演出

- P1の踏みつけ・投擲は`damageStructure`を通るため、広場周辺の建物が本当に壊れる。これを利用し、**破壊された建物の瓦礫量に応じてP2以降の足場際にも瓦礫の山ができ、落下時の受け皿になる**（10項の落下猶予と両立）。
- 導管破壊ごとに空の色/BGMレイヤーだけでなく、町の該当エリア（学生体験・ステージ・神社・飲食の各跡地）に**対応色の光が一瞬走る**演出を追加し、「壊した場所」と「壊している導管」を視覚的に一致させる。既存の `say()` テキスト通知だけでは弱い。
- 死亡時の崩落（後述12項）で、周辺の破壊可能建物に実際の物理衝撃（`hitDebris`）を伝える。既存4ボス撃破時の `spawnRagdoll` 相当のスケールを10倍にして流用できる。

## 12. 死亡演出の再設計

01案21章・9.5節「12秒以内に発光足跡を逆走」は良い方向だが、**単一クリップ（`Two Handed Sword Death`）の上に固定タイマーの逆走ルートを乗せるだけ**では、実測4.8秒のクリップに対して12秒の操作時間を後付けする形になり、崩れる身体とプレイヤーの移動が同期しない懸念がある（クリップの実尺より操作時間の方が長い）。

**再設計**: `Two Handed Sword Death` クリップの主要ボーン（肩・肘・手首）のワールド座標を実際に0.1秒刻みでサンプリングし、崩れていく身体上に**実際に動く足場**として逆算で足場Colliダーを生成する。プレイヤーはタイマーではなく「崩れる身体という動く地形」を降りる。倒れる方向をあらかじめアリーナの安全側（01案21章で既述）に固定しているため、崩落中の当たり判定は事前計算できる。

- 面白さの理由: 死亡演出中も「動く足場に乗る」という本編のコア体験（身体上戦闘）をそのまま使う。タイマー消化の演出ではなく最後の実プレイになる。
- プレイヤーの操作: 通常の移動・ジャンプ・（10項の）ウェブスイングで、崩れていく身体を降りる。
- 実装コスト: 高。クリップのボーンワールド変換を事前サンプリングし、時間軸付きの足場Colliダー列を生成する専用パイプラインが要る。
- 技術リスク: 4.8秒という短いクリップ尺に対し、降下に必要な移動距離（頭から手まで）が間に合わない可能性が高い。クリップ再生速度を落とす（0.4倍速など）か、クリップ後半をポーズ保持して尺を伸ばす調整が要る。
- 簡略版: 01案どおり固定12秒のタイマー＋発光ルートの自動誘導。ただし逆走中に1回だけ「揺れ」による軽いQTE的回避（ジャンプ入力）を挟み、完全な無風演出にはしない。標準版はこちらを採用し、高コスト版は理想版へ回す。

## 13. 削るべき要素

- **マルチプレイの部位状態snapshot同期**（01案24章リスク6）は、標準版のスコープから明示的に外す。ホスト権威で足場・部位状態を再構成する設計は、単体プレイのコア体験が固まってから着手すべきで、M0〜M9の初期実装に混ぜるとデバッグ対象が倍になる。
- **9個の足場すべてに固有名を与える**（頭頂部/肩/背中/胸/腕/手のひら/腰/脚を網羅する9.3節の例）は、要件が「すべてを使う必要はない」と明言している以上、01案の7系統部位と9足場の対応を**5〜6個に整理**した方が、UIの弱点表示（19章）も攻撃テーブルも簡潔になる。腰・手のひらは今回は「経由点」として扱い、固有の役割を持たせない。
- `four_echoes` は4ボス技の縮約再生だが、01案の攻撃表で他の技（`world_stomp` `rubble_throw` `body_swat`）と役割が重複気味。8項の `conduit_backlash` に統合し、独立技としては削る。

## 14. 追加すべき要素

- 3項で指摘したカメラ上限16mの解除（ボス戦中だけ `preview` 相当の緩和クランプを適用する専用モード）。これが無いと巨大感の演出がすべて絵に描いた餅になる。
- 5項で指摘した4ボス撃破報酬アイテムの戦闘内利用（最低でも、所持している報酬アイテムの数に応じて祭核の露出時間や導管の耐久を微調整する程度でよい）。
- 10項のボス本体を対象にしたウェブスイング拡張（`findAnchor` のボスAABB/部位対応）。

## 16. 改訂版の完全なボス戦フロー

1. **P0 祭壇の再構築**（6項）: 4体目撃破直後、ラグドール残骸が広場中央へ収束。カメラは低い位置から見上げ、操作は維持。安全時間の後、アリーナロック（半径52m、`ARENA.maxRadius: 84` の範囲内）。
2. **P1 二本の脚**: `world_stomp` `rubble_throw` の予兆を避けつつ左右すねを攻撃。片脚破壊で膝つき、地面についた前腕を坂として登れる（01案6章の主経路を維持）。両脚不要、片脚で進行可。
3. **P2 身体は戦場**: 9→5〜6系統に整理した足場を移動しながら4祭導管を任意順で破壊。`grip_shake`（8項）が登攀路上での緊張を作り、`debris_shed`（8項、簡略版はハザード化）が地上落下由来の危険を作る。ここが最も長いフェーズで、登攀・落下・ウェブスイング復帰（10項）を繰り返す。
4. **P3 視界を奪う**: 視界冠を壊すと頭部→胸ルートが開くが、9項の「両膝つき低姿勢」を使えば導管を残したまま地上から直接核を狙う裏ルートも成立する。
5. **P4 祭核**: 露出コアの脈動に合わせて攻撃と退避。`conduit_backlash`（破壊直後の一瞬の反撃）が最後まで緊張を持続させる。
6. **P5 最後の降下**: 核破壊で崩落開始。標準版は固定タイマー＋1回の回避QTEで発光ルートを降りる。プレイヤーが間に合わなくても失敗にはしない（01案どおり手が受け止める）。
7. **撃破確定**: 導管の光が町の該当エリアへ戻る演出（11項）。`finalBoss.defeated=true` を保存し、通常進行へ復帰。

## 17. Codexへ戻す具体的な宿題

1. `src/engine/step.js:134` の `c.dist` クランプ（通常時最大16m）を、ボス戦中どう緩和するか。緩和しない場合、36mの巨人がどのフェーズでも画角に収まらないことの許容判断をCodex側で明示してほしい。
2. `ThirdPersonCamera.jsx` の `cameraDistance()` はベイクされた静的地形/建物の遮蔽しか扱わない。動くボス本体とのカメラ衝突判定を、既存のベイク方式に足すのか、別モジュール（簡易カプセル線分判定）にするのか技術方式を決めてほしい。
3. 現行コードベースに `AnimationMixer` / `AnimationClip` 再生の実装は存在しない（`BossModel.jsx` は手続きQuaternion姿勢のみ）。01案16章で前提にしている実FBXクリップ再生は**新規パイプライン**であることをリスク一覧（24章）へ明記し、フォールバック（クリップ再生失敗時に手続きポーズへ切替）の具体設計を出してほしい。
4. `webswing.js` の `findAnchor` をボス本体（動くターゲット）へ拡張する場合の現実的な実装方式（`registry.parts` に依存しない距離ベース判定など）を検討してほしい。10項の落下復帰・8項のグリップ演出の実現可否に直結する。
5. 5項・14項で指摘した4ボス撃退報酬アイテムの戦闘内活用について、どの程度まで取り込むか（UI表示のみ／数値バフ／専用ギミック）の判断を標準版の範囲としてCodex側で線引きしてほしい。
6. 12項の死亡演出について、標準版（固定タイマー＋簡易QTE）と高コスト版（クリップ実軌道からの足場生成）のどちらを採用候補にするか、`Two Handed Sword Death` の実測4.8秒という短さを踏まえて判断してほしい。
