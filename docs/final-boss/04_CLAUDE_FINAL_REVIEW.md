## 03末尾の5つの再確認点への判定

1. **報酬アイテムを「導管破壊後の安全帯」だけに使う実装量で、4ボス撃破の実感として十分か。** → 十分。最小実装でも撃破順の反映（導管配置の回転）と組み合わせれば「毎回同じ戦いにならない」という02の指摘は満たす。将来の拡張余地として残せばよく、標準版のスコープ拡大は不要。
2. **低姿勢ルートを核HP25%上限にした判断は、身体上戦闘の必須性と自由度を両立できているか。** → できている。最後の75%は必ず搭乗を要求するため、要件3「身体へ乗り、登り、身体上で戦う」を迂回できない。地上短縮ルートは減点にならない。
3. **6足場でP2〜P5が単調にならないか。** → 各フェーズで有効な攻撃（`grip_shake`/`blind_charge`/`core_pulse`等）と足場の役割が変わるため、足場の数そのものより攻撃セットの差し替えで単調さは回避できている。許容範囲。
4. **`debris_shed` を単純球ハザードへ落とした判断。** → 妥当。02の技術コスト表でも標準版スコープ外(高コスト版)だった要素であり、簡略化してでも標準版に含めたのはむしろ手厚い。
5. **死亡クリップ0.4倍+実ボーン追従が12秒の余韻として間延びしないか。** → 4.8秒 ÷ 0.4 = 12秒で計算は正しく、8秒以降を手のひらでの安全待機に充てる設計は「タイマー消化」ではなく「実際に降りる」体験を保っている。間延びのリスクは低い。

以上5点はいずれも致命的ではなく、新規の大機能追加なしで進めてよい。

## 必須確認事項（プロトコル指定4点）の判定

- **カメラ16m問題**: 解決方針が具体的かつ実コードのパターン（`preview`分岐）に沿っており妥当。承認可。
- **実AnimationMixer再利用**: 転用元（`CharacterModel.jsx`）は実在し、既存ボスではなくプレイヤー側の実装を型として使うという主張は正確。承認可。
- **動く足場**: 差分行列・ヒステリシス・フレーム毎上限クランプという設計は既存の意図（急変時にプレイヤーを理不尽に飛ばさない）と整合。承認可。
- **死亡クリップ4.8秒→0.4倍**: 計算・設計とも妥当（上記5番）。承認可。
- **PC/スマホ性能と操作感**: 性能予算数値は妥当だが、**操作感の前提が崩れている**。モバイルの移動入力（`touch.move`）を書き込むUIが現状どこにも存在せず、01案が自ら「リスク7」として認めていたにもかかわらず、03案では実装対象からも技術的リスク一覧からも落ちている。身体上を歩き回って登攀する体験が中核であるラスボス戦で、モバイルの移動自体が未接続なら「スマホでも最低限遊べる」（完成条件）を満たせない。

1. **モバイル移動入力の接続をスコープへ明記する。** `touch.move` へ書き込む最低限の仮想ジョイスティックUIを、既存4ボス・通常ステージにも影響する共通基盤として実装計画に含める（M11またはそれ以前）。ラスボス専用ではなく既存ゲーム全体の欠落だが、身体上移動が主要ゲームプレイになる本機能はこれなしでは「スマホで最低限遊べる」を満たせないため、`10_IMPLEMENTATION_PLAN.md` で明示的にマイルストーンとタスクオーナーを割り当てること。新規の大機能ではなく、既存 `touch.move` 変数を実際に駆動する最小限のUIでよい。
